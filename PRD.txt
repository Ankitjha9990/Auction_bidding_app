# Product Requirements Document
# Real-Time Tournament Auction Platform

**Version:** 1.0  
**Product Type:** Real-Time Web Auction Platform  
**Primary Use Case:** College Tournament / Sports Player Auction  
**Primary Goal:** Enable administrators to conduct a fast, reliable, visually engaging live player auction while allowing team captains to bid in real time and spectators/players to monitor the auction.

---

# 1. Product Vision

Build a **premium, fast, real-time tournament auction web application** where:

- An **Admin** creates and controls an auction.
- **Team Captains** participate in live bidding.
- **Players/Viewers** watch the auction in real time.
- Every bid, budget change, player status change, and auction event propagates to connected users **without page refresh**.
- The interface should feel like a professional sports auction rather than a generic admin dashboard.

The application should prioritize:

> **Speed → Real-time synchronization → Clear auction state → Visual quality → Reliability**

The application must remain usable even when many users are simultaneously connected.

---

# 2. Core User Roles

There are exactly three primary roles.

| Role | Access |
|---|---|
| Admin | Complete auction management |
| Captain | Real-time bidding for their team |
| Player / Viewer | Read-only live auction information |

---

# 3. Role 1 — ADMIN

The Admin is the controller of the entire auction.

The Admin should have complete authority over:

- Auction creation
- Team creation
- Captain assignment
- Player registration
- Player images
- Player metadata
- Budgets
- Player categories
- Auction order
- Player nomination
- Bid management
- Bid increments
- Auction timer
- Sold / Unsold status
- Re-auction
- Undo / correction
- Auction pause/resume
- Live dashboard
- Results
- Reports

---

# 4. Role 2 — TEAM CAPTAIN

Each team captain receives an authenticated account.

The captain can:

- Join the active auction
- View current player
- See player information
- See current highest bid
- See current highest-bidding team
- See their remaining budget
- See their squad
- See their remaining slots
- See eligible bid amount
- Place a bid
- Receive instant bid updates
- Receive auction timer updates
- See when a player is SOLD
- See when a player is UNSOLD

The captain **cannot**:

- Modify player information
- Modify team information
- Modify budgets
- Change auction state
- Change bid increments
- Change another team's data
- Delete bids
- Access admin controls

This should essentially be a **read-only live auction experience**.

Viewer can see:

### Current Auction

- Current player

- Player status

### Auction Progress

- Players sold

- Total players

- Team budgets
- Players purchased by each team
- Recent bids

Viewer cannot interact with the auction.

Do **not** implement live bidding using:


```text

Realtime Server
   │
   ├── Auction Engine

```

Possible stack:

```text

Realtime
```

For the **highest control over auction concurrency**, I would architect the bidding engine as a server-authoritative service rather than trusting the frontend.

# 24. SERVER-AUTHORITATIVE BIDDING

This is critical.

Never allow:

```text
Frontend
→ Database
```

to directly determine whether a bid is valid.

Instead:

```text
Captain
   ↓
Bid Request
   ↓
Server
   ↓
Validate
   ↓
Atomic Transaction
   ↓
Update Auction State
   ↓
Broadcast Event
   ↓
All Clients
```

The server decides:

- Is auction live?
- Is player currently active?
- Is captain authorized?
- Does team have enough budget?
- Is bid greater than current bid?
- Is bid increment valid?
- Has timer expired?
- Is team allowed to bid?
- Is the team already full?

# 26. CONCURRENT BID PROTECTION

This is extremely important.

Imagine:

```text
Captain A clicks ₹10,000
Captain B clicks ₹10,000
```

at almost exactly the same time.

The backend must ensure that **only one valid bid wins**.

Use:

- Database transaction
- Row-level locking / atomic update
- Server-side sequence number
- Server timestamp

Example:

```text
Bid #103
₹10,000
Team A
Server Timestamp: 21:14:32.281
```

Team B should receive:

```text
Bid rejected.
Current bid is now ₹10,000.
```

No duplicate auction state should ever occur.

# 29. TIMER

The timer must be **server-authoritative**.

Do not simply count:

```javascript
setInterval(() => timer--, 1000)
```

because different clients will drift.

Instead server maintains:

```text
auction_started_at
auction_ends_at
```

Clients calculate:

```text
remaining =
auction_ends_at - server_time
```

The UI can animate the countdown locally, but the server remains authoritative.

# 47. EVENT SEQUENCE NUMBERS

Every auction event should have:

```text

```

```text

102
103
104
```

```text
101
102
104
```

it knows:

```text

```

and can request state reconciliation.

This prevents realtime synchronization bugs.

# 92. ACCEPTANCE CRITERIA

The application is considered successful when:

### Authentication

- Each role sees only its permitted interface.
- Captain cannot access admin controls.
- Viewer cannot place bids.

### Auction

- Admin can start an auction.
- Admin can select a player.
- All connected clients see that player automatically.

### Bidding

- Captain can place a valid bid.
- Invalid bids are rejected server-side.
- Two simultaneous bids cannot corrupt auction state.
- Budget updates automatically.

### Realtime

When Team A bids:

```text
Captain A
Captain B
Admin
Viewer 1
Viewer 2
```

all should receive the new auction state without refreshing.

### Timer

Timer remains synchronized across clients.

### Sold

After auction ends:

```text
Player → SOLD
Team → receives player
Budget → deducted
```

all atomically.

## One additional recommendation

For your actual implementation, I would make the **Live Auction screen a completely separate application shell from the normal Admin dashboard**.

In other words:

```text
/admin
```

for management,

```text
/captain
```

for bidding,

and

```text
/live/:auctionId
```

for the public screen.

That lets you make `/live` extremely lightweight and fast. You can even open it on a **large projector/LED screen at the tournament**, while captains use their phones/laptops and the admin controls everything from another device.

The result becomes less like a normal college website and more like an actual **live auction control system**.
